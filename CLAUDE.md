# CLAUDE.md — SSBM Stats

## What this is

A zero-backend web app: a Melee player points their browser at their local Slippi replay folder and gets a stats dashboard. All parsing happens client-side via `@slippi/slippi-js` in web workers. The privacy contract, precisely:

1. **Raw `.slp` files never leave the machine — hard product constraint, no exceptions.**
2. Parsed `GameRecord` stats (~5 KB/game — ~1 KB of headline stats plus the per-move table) may sync, but only **opt-in**, only to **the Supabase project that deployment is configured against** — the user's own when self-hosted, the operator's on ssbmstats.com — behind `VITE_SUPABASE_URL`/`VITE_SUPABASE_ANON_KEY` env vars, with per-user row-level security. Without those vars `supabase` is `null`, `CloudSync` renders nothing, and the app is exactly the local-only tool described here. Never tell a hosted user their stats sync to "their own Supabase": on ssbmstats.com those rows sit in the operator's project, isolated per user by RLS. "Your private account" is the honest claim; the stronger one is a privacy misstatement.
3. No telemetry, analytics, or any other non-opt-in transmission of **replay-derived** data — ever. Aggregate visit counting is the one exception, and it never touches replay data: the hosted ssbmstats.com mounts Vercel Web Analytics (`<Analytics />` in `main.tsx`), which is cookieless, identifies no one, and reports page views, referrers, and country only. It loads `/_vercel/insights/script.js`, which exists solely on Vercel, so a self-hosted build carries the mount inertly and transmits nothing.

## Architecture

```
folder pick ─► discovery (*.slp) ─► dedup vs IndexedDB ─► worker pool (slippi-js)
                                                              │ GameRecord (~5 KB)
              React dashboard ◄── memoized selectors ◄── IndexedDB (Dexie)
                                                              │ opt-in, stats only
                                                        Supabase (user's own project)
```

- `src/lib/pool.ts` — file discovery (FS Access API + `webkitdirectory` fallback), worker pool sized to `hardwareConcurrency`, clamped to 8 (and defaulting to 4 when the browser won't say). DB flushes are batched (25 records) on a promise chain — storage failures surface as `RecordSaveError` after the run, never as silent loss. UI delivery is time-throttled (~1 s for records, 250 ms for progress counts) because every record append invalidates App's O(n log n) resolve+sort. An `AbortSignal` (App's reset) stops feeding, flushing, and callbacks; parsed-but-unflushed work is dropped by design.
- `src/worker/parser.worker.ts` + `src/lib/parse.ts` — one replay → one `GameRecord`. Stats-only: frame data is computed over then discarded. Corrupt files get tombstone records (`parseError` set) so they're never re-parsed.
- `src/lib/db.ts` — Dexie/IndexedDB. Cache key is `path|size|mtime` — that is a *file* key, answering "have I parsed this file?"; game identity is separate (see `dedupe.ts` and decision 8). `kv["myAccounts"]` holds the user's `Account[]`, with a read-fallback to the pre-multi-account `kv["myCodes"]` string array — that fallback is the local migration path and must outlive the cloud one, since no backfill ever ran against anyone's IndexedDB; drop it and an existing user lands back on the identity prompt with a full cache. Records live packed ~250/row (`packs`) with an id-only `seen` table for dedup — per-row IndexedDB overhead made 30k-game restores slow. Browser-local; optionally mirrored to the user's own Supabase when cloud sync is configured. Also stores the picked `FileSystemDirectoryHandle` in `kv` so a return visit can re-walk the folder without re-prompting: the app auto-rescans on load when the permission is still granted, and the topbar **Refresh** button re-requests it (needed after a browser restart) — both dedup against the cache, so only new replays parse. **Change folder** is the full reset (`clearAll` + abort + generation bump).
- `src/lib/stats.ts` — identity inference + all aggregation selectors. Pure functions over `ResolvedGame[]`.
- `src/lib/dedupe.ts` — `gameKey(rec)`, a content-derived identity (`playedAt|stageId|sorted player sides`) that survives the replay folder being copied, moved, or synced through a service that rewrites mtimes, plus `dedupeRecords()`. See decision 8.
- `src/lib/model.ts` + `src/worker/model.worker.ts` — logistic-regression win model (IRLS, O(iterations·n·k²)) fitted in a worker with plain-data in/out; `null` model means "not enough data". `src/lib/coach.ts` — z-score- and sample-size-gated recommendations. Both feed the Insights view, which caches fits by games-array identity so tab revisits don't refit.
- `src/lib/supabase.ts` / `src/lib/cloudSync.ts` / `src/components/CloudSync.tsx` / `supabase/schema.sql` — optional cloud sync. Cloud rows are keyed `(user_id, id)` where `id = path|size|mtime`, so re-parsing the same files anywhere upserts idempotently. Sync is a two-way id diff: push local-only non-tombstone records (500-row chunks), pull remote-only ones straight into the local cache. The landing page's "Sign in with Google to restore" covers the fresh-device case (empty local cache ⇒ pure pull, including saved accounts). **Only games one of the user's own accounts played are pushed** (`isSyncable`): a shared replay folder holds housemates' games too, and those are cached locally — identity is query-time, so adding an account later has to be able to claim them — but uploading someone else's stats isn't the user's call. The same predicate must gate CloudSync's `pending` count, or foreign games stay unsynced forever and pin the button gold. The pull stays unfiltered: RLS already scopes it, and filtering would break the fresh-device restore, which syncs before it knows the accounts. Pushes carry a `game_key` and skip a record whose game is already up there under a different file key, so a moved folder can't double the cloud copy; rows predating that column are unkeyed and simply don't participate, because correctness lives in the client-side dedup, not the column. `user_codes` (one row per account, with `label` and `sort_order`) is the identity store. It replaced a `user_settings.my_codes text[]`, which the schema's guarded backfill copies across; nothing reads or writes that table any more, so a project still carrying it can drop it. Sync is automatic — on sign-in, ~2.5 s after newly parsed games stop streaming in, and on tab re-focus (≥60 s apart) — so every signed-in device converges to the union without user action; the header button turns gold with a count only as the manual fallback when an auto-sync failed (offline). One auto-push attempt per pending count: failures must not retry-loop.
- `src/lib/demo.ts` — deterministic synthetic data (seeded PRNG); keep it deterministic.
- `scripts/lib/gif-encode.mjs` + `scripts/lib/gif-draw.mjs` — the shareable-animation pipeline: a from-scratch GIF89a encoder (LZW, one global popularity palette) and the frame painters. **Plain JS with `.d.mts` siblings on purpose** — the identical modules are imported by the browser (the Share GIF buttons, via dynamic import so they stay out of the tab's chunk) and by Node (`scripts/render-liquipedia-assets.mjs`, headless via `@napi-rs/canvas`), and Node can't load `.ts`. Fonts are generic stacks because CI has neither Chakra Petch nor IBM Plex Mono. Generated assets land in `public/share/` (gitignored) and are **rendered during the Vercel deploy** via `npm run build:deploy`, never committed — a re-rendered GIF is ~2.5 MB of binary that can't delta-compress, so committing them on each data change would grow the repo without bound. A failed render must not fail the deploy, hence the `|| echo` in that script. They're also excluded from the PWA precache (`globIgnores`): a multi-megabyte GIF has no business in the offline bundle. Both paths sample the race through the same `sampleFrameIndices` helper — which always keeps the final frame, since that's the one the loop holds on — so an exported GIF and a served one contain the same frames.
- `src/lib/liquipedia/` + `src/components/liquipedia/` + `scripts/refresh-liquipedia.mjs` — the **Liquipedia tab**: scene-wide Melee history (majors, SSBMRank editions, career winnings), the one view that shows nothing about the user's own replays. `data.ts` is a **generated bundled snapshot**, not a runtime fetch: the app has no backend and the CSP allows self + Supabase only, so the dataset ships in the (lazy) chunk and works offline. A weekly GitHub Action (`.github/workflows/liquipedia-refresh.yml`) runs the refresh script and commits `data.ts` alone; share images are a deploy-time artifact, not a tracked one. The refresh is **append-only** — it adds majors and ranking editions not already present (deduped on name+year, never on date, or an event listed late would be invisible forever) and never rewrites existing rows, so a parser miss costs an update rather than the dataset. It bails loudly if more than 25 majors look new, since that means the parser drifted rather than that history changed. It exits 2 when Liquipedia rate-limits it, which the workflow treats as "nothing to do". The one thing it revisits is a player whose winnings are still unknown. Because append-only means a parser fix can't reach existing rows, `scripts/rebuild-liquipedia.mjs` re-derives everything from the source pages; it stays manual since a `--force` run is two requests per champion 30 s apart (~30 min today); without `--force` it reuses known winnings and fetches only the two index pages. Fetching, and reading/writing `data.ts`, live in `scripts/lib/liquipedia-fetch.mjs` and `liquipedia-data.mjs` so both paths share one definition.
  - **The figures live in rendered HTML, not wikitext.** Majors parse from `prop=text` (the `divRow`/`tournament-card-premier` markup, where the premier class is the only supermajor signal — miss it and the count reads ~30% low), rankings from `prop=wikitext` (`{{PRplayer}}`, where `{{!}}` is an escaped pipe that will truncate a name if you match templates naively), and career winnings only from the rendered player page. Two parsers were written against the wrong source before this was understood; `scripts/inspect-liquipedia-page.mjs` plus the **Inspect Liquipedia page** workflow exist to print the real markup rather than guess, and to do it from a runner, because Liquipedia blocks a developer IP for hours after any burst.
- `src/components/` — Overview (+ ShareCard PNG export), Teams, Sessions, Insights, Records, MetricsGuide, CloudSync, FilterBar, Landing, and Views.tsx (Matchups, Stages, Opponents, Execution, GameLog), plus the identity/chrome pieces: AccountsEditor (the multi-account editor from decision 1), AccountFields, ProgressAndIdentity, Kpi, GoogleG. Views are lazy chunks — which is why the PWA precache must cover everything. `src/main.tsx` is the entry point and owns service-worker registration (see Deployment).

## Key decisions (do not silently reverse)

1. **Players are stored neutrally** in `GameRecord.players[]` with `winnerIndex` (singles) / `winnerTeamId` (teams), NOT as self/opponent. Identity (the user's connect code(s)) is chosen after parsing and applied at query time (`resolveGames` / `resolveTeamGames`). This makes alt accounts and identity changes free. Never bake "self" into the stored record.
   - **The user has an `Account[]`, not a code.** One person routinely owns a main and an alt whose replays land in the same folder; every account is "you", games are pooled across all of them, and `Filters.accountCode` splits them back apart. Labels ("Main", "Alt") are display only — resolution matches on `code`. They render as `Main (ABCD#123)` in dropdowns via `accountLabel()`, and as the bare label in dense tables via `codeShort()`. Because identity is query-time, the Accounts editor changes it with a recompute and **never a re-parse or a cache clear** — do not route account edits through the "Change folder" reset.
   - **Two of the user's own accounts in one game** (`selfMatch`) carry no result: `isWin` is forced null, which excludes them from every win-rate denominator for free, and they are skipped in `byOpponent`, `byTeammate`, `byTeammateDamage` and the card's rival. They stay visible in the game log, badged "self". Rare in practice — it needs a lent account — but the alternative is crediting a coin-flip win to whichever port sorted first.
   - **Singles vs teams is an axis separate from `gameType`** — a 2v2 is still ranked/direct/offline. `Filters.format` switches the dashboard between the singles tab set and the single consolidated `Teams` view; the two never mix in one aggregation. Teams selectors resolve me/teammate/opps and win/loss at the team level. `resolveTeamGames` skips anything that isn't a clean 4-player two-team game rather than guessing a teammate.
2. **Win/loss ladder**: gameEnd placements → stock-out survivor → LRAS initiator loses. Games under 30 seconds are `winnerIndex: null` (indeterminate) and excluded from win-rate denominators but still shown in the game log.
3. **Frames are discarded.** Custom frame-level metrics (wavedash quality, ledgedashes) are a future feature behind an explicit opt-in re-parse — don't retain frames to make a feature easier.
   - When a new per-game stat is added, bump the Dexie version and **clear `packs` + `seen`** (see the v9–v11 migrations in `db.ts` for the template; `games` is a legacy empty store since v8). A one-time full re-parse beats mixed-schema rows silently understating averages; don't build per-row schema versioning or lazy re-parse machinery for this.
4. **The "By mode" panel on Overview ignores the mode filter** (applies all other filters) so overall/ranked/unranked/direct rows are always all visible for comparison. Preserve this when refactoring filters.
5. **Only tournament-legal stages count** — `INCLUDED_STAGE_IDS` in `src/lib/config.ts`; games on other stages are dropped at resolve time and never reach any view.
6. **The Liquipedia tab is bundled, cited, and append-only.** It is public scene history, so it deliberately ignores the global `Filters` (a note in the view says so) and never touches replay data — which is also why it's reachable straight from the landing page (`browsingHistory` in `App.tsx`), not only as a dashboard tab. Character identity there uses full names (`src/lib/liquipedia/chars.ts` maps them to the existing `/public/stock` sprites), not Slippi character IDs. Every panel traces to a listed source, and the Sources panel must keep the CC BY-SA 3.0 attribution — don't add a claim the dataset can't support.
   - **Offline majors only.** Netplay events (Liquipedia's venue column reads "Online") are flagged `online: true` at parse time and filtered out of every total, including the rendered share assets; the view states the exclusion and the count. This is a judgement call, not a data cleanup: 16 events, and it moves Zain from 33 titles to 24, because individual weeks of an online league were counted beside Genesis. Keep the rows flagged rather than deleted so the choice stays auditable.
   - **Winnings are all-Smash and labelled as such.** Liquipedia's "approx. total winnings" covers every Smash title a player entered, and there is no per-game breakdown on the page to quote — only a sum we could compute ourselves from the results tables, which would be our number, not theirs. Don't relabel the column as Melee earnings without doing that work.
7. **Priority of stats** (per owner): kills and win rates — by opponent (connect code), by opponent character, by own character — come first; execution metrics (L-cancel %, openings/kill, damage/opening, IPM) second. Sessions exist (a session = games separated by <30-minute gaps — that boundary is load-bearing for the tilt tables; don't change it casually).
8. **File identity and game identity are different things.** `GameRecord.id` (`path|size|mtime`) answers "have I parsed this file?" and stays the cache/`seen`/cloud primary key — it is what makes a rescan cheap. It is *not* a game identity: copying a replay folder changes every path, a Dropbox/Drive/SMB share rewrites mtimes, and re-organizing into per-month subfolders changes both, each producing a second record for a game already held and inflating game counts, hours, and win-rate denominators. `gameKey()` in `dedupe.ts` derives game identity from the replay's own contents instead. Three layers apply it: `dedupeRecords` in App between records and resolve (the correctness guarantee — it covers cache, scan and cloud-pull alike), `pruneDuplicates` at startup (storage), and the `game_key` skip in `pushMissing`/`pullMissing` (stops copies crossing the wire). The survivor is deterministic — real record over tombstone, then lowest id — because those three sources race, and an order-dependent survivor would change a game's React key between loads. **`pruneDuplicates` deliberately leaves the dropped ids in `seen`**: those files still exist on disk, and forgetting them would re-parse the copies and recreate the duplicates on the next scan.

## Design system

Dark GameCube-indigo theme, tokens in `src/index.css` (`--bg #121022`, accent `#8f7ff7`, win `#3fcf8e`, loss `#f0564f`, gold `#e8b54d` = attention, e.g. unsynced games). Fonts: Chakra Petch (display), Inter (body), IBM Plex Mono (data — always tabular numerals for stats). Win-rate coloring goes through `winRateColor()` in `src/lib/format.ts`; don't introduce ad-hoc greens/reds. Chart styling goes through `src/components/chartStyle.ts` (`axisStyle`, `tooltipStyle`, `gridStyle`, `dayTick`); **red is reserved for loss/danger** — comparison series like opponent overlays use `OPP_SERIES_COLOR` (muted, dashed), never red.

Categorical series colors (the Liquipedia character charts) come from `CHAR_COLORS` in `src/lib/liquipedia/chars.ts`: a fixed 7-hue order validated for colorblind separation against the `--panel` surface, with everything past it folded into a single `Other` grey — never generate an eighth hue. `CHAR_STACK_ORDER` is that validated adjacency, and the clustered per-edition bars render in it — keep that, since the CVD guarantees were measured on neighbouring pairs. The year explorer sorts by head-count instead, so its hues land in an arbitrary order; that's fine because every row there carries a stock icon and a name, and colour isn't doing the identifying. Ordinal splits (major vs supermajor) use two steps of one hue instead, and pair them with a legend plus a tooltip listing the underlying rows, since the dim step sits under 3:1 on this surface.

## Conventions

- TypeScript strict **plus `noUncheckedIndexedAccess`** — indexing returns `T | undefined`; use the guard-then-`!` pattern already established in `pool.ts`/`parse.ts` rather than weakening types. `npm run build` (tsc + vite) must pass before any push.
- Selectors in `stats.ts` must be single-pass O(n) — libraries can reach 30k+ games.
- **Day/week bucketing is local time** (`localDay` and friends in `stats.ts`) — never `toISOString()` for day keys; date-only strings parse as UTC and shift a day west of Greenwich.
- New aggregate views: respect the global `Filters` and the click-to-filter pattern (clicking a row/cell scopes the dashboard).
- Sample-size honesty: any win-rate display over small n should fade or badge it (see matchup matrix `minGames`).
- Smoke-test selectors against demo data (`generateDemoRecords`) when touching `stats.ts`.
- **Commits are authored as `Studio Pinball <info.studio.pinball@gmail.com>`** — the same address the app publishes as its contact. `.githooks/pre-push` refuses to push anything else. Git will not run a tracked hook until the clone opts in, so a fresh clone needs `git config core.hooksPath .githooks` once; without it the guard is silently absent.

## Deployment

Vercel, deploying `main`. Three things to know before touching config:

- **PWA**: `vite-plugin-pwa` precaches the entire shell — all lazy chunks, fonts, icons — so the app works offline. If you add a new asset *type*, check `globPatterns` in `vite.config.ts` covers it. Registration is **manual** (`injectRegister: null` in `vite.config.ts`): `src/main.tsx` registers the SW itself and polls `registration.update()` hourly so a tab left open picks up new deploys — don't re-enable the plugin's auto-registration, which would silently drop that poll.
- **Build identity**: `__BUILD_ID__` (defined in `vite.config.ts` from the git commit, declared in `src/global.d.ts`) is stamped into the footer in `App.tsx` — the deployed commit is user-visible, which is how you verify a deploy actually rolled.
- **CSP** in `vercel.json` allows connections only to self + `*.supabase.co`. Any new network destination must be added there deliberately — a blocked request in production is the symptom.

## Commands

```bash
npm install
npm run dev      # dev server; use demo mode on the landing page if no replays
npm run build    # type-check + production build — must pass before any push (nothing in CI gates it)

node scripts/refresh-liquipedia.mjs         # top up the bundled scene dataset (the weekly Action runs this)
npm run assets                              # render public/share/*.gif|png (gitignored; the deploy does this too)
node scripts/rebuild-liquipedia.mjs         # re-derive the whole snapshot (add --force to refetch players, ~30 min)
node scripts/inspect-liquipedia-page.mjs Hungrybox 'winnings'   # print real markup when a parser stops matching
```
